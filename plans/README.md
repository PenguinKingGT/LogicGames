## Target architecture

```text
/                         static, server-rendered game menu
/games/mastermind         one full-screen Client Component game route
/games/polymine           one full-screen Client Component game route
                                  |
                                  +-- Phaser loaded dynamically in browser only
/games/nonogram           one DOM-based Client Component game route (planned)
```

Application-owned code lives under `src/`; migrated game code is namespaced
under `src/games/<slug>/`. Neither source repository is a runtime dependency.
The menu and route pages remain Server Components; browser state, storage,
audio, and Phaser are contained behind game-specific Client Component
boundaries.

## Architectural decisions

- Use Next.js App Router, TypeScript, pnpm, Tailwind CSS 4, ESLint, Vitest,
  Testing Library, and jsdom.
- Give every game a real page route. Do not render games in a home-page modal,
  iframe, tab panel, or catch-all runtime registry.
- Keep the existing pure game engines and their tests. Adapt application
  composition and browser boundaries; do not rewrite proven rules.
- Copy source into `LogicGames`; do not use filesystem imports, git submodules,
  or workspace links to sibling repositories.
- Keep `polymine:v1` and `mastermind:settings:v1` storage keys so data remains
  namespaced and future schema migrations remain possible.
- Keep the two icon libraries during migration. Route-level code splitting
  contains their cost; icon consolidation is cosmetic follow-up work.
- Keep Phaser out of the home and MasterMind module graphs. Load it only from a
  PolyMine Client Component using `next/dynamic` or a browser-only dynamic
  import.
- Implement Nonogram as a DOM grid with a pure reducer. Keep its test-only
  uniqueness solver out of the route import graph and do not add a renderer or
  state-management dependency.
- Isolate game CSS and CSS variables by a game root namespace. A game may not
  assign its palette globally on `:root`, `html`, or `body`.
- Do not enable `output: "export"` until a deployment target requires it. The
  app has no backend requirement, but deployment configuration is separate
  from this migration.

## Findings considered and rejected

- Combine both games into one stateful page: rejected because it loads more
  JavaScript on the menu, weakens browser history and deep links, and makes
  storage, keyboard listeners, audio, Canvas, and CSS lifecycles interfere.
- Rebuild PolyMine in DOM or MasterMind in Phaser: rejected because each source
  project already chose an appropriate renderer and has passing regression
  coverage. Replatforming adds risk without helping the collection shell.
- Create a generic plugin API for two games: rejected as premature. A typed
  static catalog is enough for menu metadata; route modules should own their
  runtime integration.
- Introduce shared game state or a global state library: rejected. Both games
  are local, independent sessions and already have suitable state boundaries.
- Add accounts, backend APIs, online leaderboards, or cross-game progression:
  out of scope for the requested two-game migration.
- Add Playwright in the initial migration: deferred. Vitest preserves both
  engines and component flows; browser E2E should be added when CI and the
  deployment/browser matrix are defined.
- Generate arbitrary Nonogram bitmaps at runtime: rejected for plan 005 because
  derived clues can have multiple solutions. The first release uses curated
  puzzles guarded by an exactly-one-solution test.
- Render Nonogram with Canvas/Phaser: rejected because a DOM grid provides
  better clue layout, focus semantics, keyboard access, and smaller route cost.
